# Getting started

doorman runs your MCP server, guards it behind a password, and exposes it so
Claude can connect. This guide goes from nothing to a working connector.

## 1. Install

See the [install table in the README](../README.md#install). Verify:

```sh
doorman --version
```

## 2. Set it up

```sh
doorman init
```

`init` asks:

- **Your MCP server.** Let doorman run it (recommended) and give the start
  command, e.g. `npx -y mcp-picnic --enable-http --http-port 3000`, its port, and
  the MCP path (`/mcp`). Because doorman runs it on `127.0.0.1` where only doorman
  can reach it, **there's no upstream token to configure**. (Or point doorman at
  an already-running server, in which case it asks whether that server needs an
  auth header.)
- **A public address.** Claude is in the cloud, so it needs a public HTTPS URL:
  - **Tailscale set up** → doorman reads your tailnet name and derives the URL,
    then offers to bring up a Funnel. Nothing to type.
  - **Tailscale not installed** → doorman offers to guide you through installing
    it and waits, re-checking; or you decline and give it a URL you already have.
- **Owner password.** Press Enter to accept a generated one. This is the key
  anyone must type to approve Claude — keep it safe.
- **Run on boot?** doorman installs a service (systemd user unit / launchd agent
  / Windows logon task) that also starts it now.

It prints the values to paste into Claude.

## 3. Add the connector in Claude

1. **Settings → Connectors → Add custom connector.**
2. **URL** = what `init` printed — it ends in **`/mcp`** (the most common mistake
   is dropping that; see [troubleshooting](troubleshooting.md)).
3. Claude registers automatically; if it asks under **Advanced**, paste the
   Client ID / Secret `init` printed.
4. Approve on doorman's consent page with your **owner password**.

Verify the whole path any time:

```sh
doorman doctor
```

## Multiple servers on one machine

Every command takes an instance name (default `default`). Each instance gets its
own local port, Tailscale Funnel port (443, then 8443, then 10000), config, and
service:

```sh
doorman init picnic
doorman init n8n
doorman list
doorman delete n8n     # stops the service, turns off its funnel, removes its config
```

Tailscale Funnel offers three ports per machine, so up to three instances can be
funnelled that way; beyond that, put them behind your own reverse proxy.

## Where things live

Per instance, under `~/.config/doorman/<name>/` (`%APPDATA%\doorman\<name>\` on
Windows), mode `0600`:

- `config.toml` — settings + secrets
- `signing_key.pem` — the RSA key that signs tokens (delete to rotate; invalidates all tokens)
- `clients.json` — DCR-registered clients

## Configuration reference

Precedence: env var > `config.toml` key > default.

| `config.toml` key | Env var | Default | Notes |
|---|---|---|---|
| `issuer_url` | `DOORMAN_ISSUER_URL` | — (required) | public base URL, no trailing slash |
| `bind` | `DOORMAN_BIND` | `127.0.0.1:8080` | local listen address |
| `spawn_cmd` | `DOORMAN_SPAWN_CMD` | — | command doorman runs + supervises as the upstream |
| `upstream_url` | `DOORMAN_UPSTREAM_URL` | `http://127.0.0.1:3000` | |
| `upstream_path` | `DOORMAN_UPSTREAM_PATH` | `/mcp` | |
| `upstream_header` | `DOORMAN_UPSTREAM_HEADER` | `Authorization` | `Authorization` (Bearer), a custom header (raw), or `both` |
| `upstream_token` | `DOORMAN_UPSTREAM_TOKEN` | — | omit for a no-auth / doorman-run upstream |
| `owner_password` | `DOORMAN_OWNER_PASSWORD` | — (must be present) | gates consent; empty allowed but not recommended |
| `client_id` / `client_secret` | `DOORMAN_CLIENT_ID` / `_SECRET` | generated by `init` | pre-registered client (works alongside DCR) |
| `funnel_port` | `DOORMAN_FUNNEL_PORT` | set by `init` | Tailscale Funnel port (443/8443/10000) |
| `allowed_redirect_uris` | `DOORMAN_ALLOWED_REDIRECT_URIS` | Claude's callback | comma-separated exact allowlist for the pre-registered client |
| `access_ttl` / `refresh_ttl` | `DOORMAN_ACCESS_TTL` / `_REFRESH_TTL` | 3600 / 60d | seconds |
| `code_ttl` | `DOORMAN_CODE_TTL` | 120 | seconds, capped at 120 |
| `rate_limit` | `DOORMAN_RATE_LIMIT` | 30 | requests/min per IP on auth endpoints; `0` disables |
| `proxy_min_interval_ms` | `DOORMAN_PROXY_MIN_INTERVAL_MS` | 0 | min milliseconds between proxied upstream calls; paces (delays, never rejects) a burst so a rate-limited upstream API stays under its threshold; `0` disables |
| `key_path` / `clients_path` | `DOORMAN_KEY_PATH` / `_CLIENTS_PATH` | in the instance dir | |
| — | `DOORMAN_CONFIG` | `<instance dir>/config.toml` | override the config path (Docker) |

Config is read at startup, so after editing `config.toml` apply it with `doorman restart [name]` (or `systemctl --user restart doorman-<name>` / relaunch `doorman run` if you run it in the foreground).
